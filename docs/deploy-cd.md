# Деплой на сервер после прохождения CI

После успешного прохождения всех проверок (backend, frontend, e2e) при **push в `main`** workflow автоматически запускает шаг **Deploy**: по SSH заходит на сервер и обновляет код, пересобирает бэк и фронт, перезапускает бэкенд.

## Что нужно настроить

### 1. Секреты в репозитории GitHub

В репозитории: **Settings → Secrets and variables → Actions** добавь:

| Секрет        | Описание |
|---------------|----------|
| `SSH_HOST`    | IP или домен сервера (например `46.29.162.75`) |
| `SSH_USER`    | Пользователь для SSH (например `root` или `deploy`) |
| `SSH_PRIVATE_KEY` | Приватный SSH-ключ (содержимое файла без пароля). На сервере в `~/.ssh/authorized_keys` должен быть соответствующий публичный ключ. |

### 2. Путь к проекту на сервере

В workflow зашит путь **`/var/www/on`**. Если у тебя проект лежит в другом каталоге, измени в `.github/workflows/ci.yml` в шаге **Deploy via SSH** строку:

```yaml
cd /var/www/on
```

на свой путь.

### 3. Имя процесса PM2

Сейчас в скрипте: `pm2 restart on-backend`. Если бэкенд зарегистрирован под другим именем, замени в `ci.yml` на своё (или убери `|| true`, если pm2 не используешь и перезапускаешь бэкенд иначе).

### 4. Git на сервере

- В каталоге проекта должен быть клон репозитория (`git clone ...`).
- По `git pull origin main` сервер должен подтягивать изменения без запроса пароля (доступ по SSH-ключу, тот же ключ что в `SSH_PRIVATE_KEY`, или отдельный deploy-ключ с доступом на pull).

### 5. Фронт при сборке на сервере

Для продакшена фронт должен собираться с нужным API URL. На сервере в `frontend/.env` задай, например:

```bash
VITE_API_URL=https://твой-домен.com/api
```

или оставь пустым, если у тебя в коде уже есть подстановка через `window.location.origin + '/api'`. После этого `npm run build` в шаге Deploy создаёт актуальный `frontend/dist/`, который раздаёт nginx.

### 6. Письма (сброс пароля и уведомления)

Чтобы отправлять письма сброса пароля, на сервере в окружении бэкенда задай `FRONTEND_URL` и SMTP-переменные. Подробно: **[docs/email-setup.md](email-setup.md)**.

### 7. Бэкапы SQLite (B34)

На сервере можно запускать резервное копирование SQLite командой:

```bash
cd /var/www/on/backend
npm run backup
```

Полезные переменные окружения бэкенда:

- `BACKUP_DIR` — папка для бэкапов (по умолчанию `./backups`).
- `BACKUP_RETENTION_DAYS` — срок хранения бэкапов в днях (по умолчанию `7`).

Пример `crontab` (ежедневно в 03:00):

```bash
0 3 * * * cd /var/www/on/backend && /usr/bin/npm run backup >> /var/log/on-backup.log 2>&1
```

## Как это работает

1. Ты пушишь в `main` (или мержишь PR в `main`).
2. Запускаются jobs: Backend, Frontend, E2E.
3. Если все три успешны и событие — **push** в **main**, запускается job **Deploy to server**.
4. Runner подключается по SSH к серверу и выполняет:
   - `cd /var/www/on && git pull origin main`
   - в `backend`: `npm ci && npm run build && pm2 restart on-backend`
   - в `frontend`: `npm ci && npm run build`
5. Nginx продолжает отдавать `frontend/dist/` и проксировать `/api/` на бэкенд — обновлённые файлы уже там.

На **pull request** деплой не запускается, только проверки.

## Если изменения не появляются на сервере

1. **Деплой только при push в `main`**  
   При мерже PR через «Merge pull request» GitHub делает push в `main` — тогда деплой должен запуститься. Если пушишь в другую ветку, деплой не запускается.

2. **Проверь вкладку Actions**  
   Открой последний workflow run для ветки `main`. Убедись, что job **Deploy to server** есть в списке и выполнился без ошибок (зелёная галочка). Если он красный — открой его и посмотри лог шага «Deploy via SSH»: там будет вывод команд с сервера (в т.ч. ошибки `git` или `npm`).

3. **Путь на сервере**  
   В скрипте деплоя зашит каталог `/var/www/on`. На сервере проект должен лежать именно там (или измени путь в `ci.yml`). Изначально его нужно создать и сделать там `git clone <твой-репо> .`.

4. **Доступ Git к репозиторию**  
   На сервере в `/var/www/on` при выполнении `git fetch origin main` репозиторий должен тянуть данные с GitHub без запроса пароля (по SSH-ключу или по HTTPS с сохранёнными учётными данными). Если клон по HTTPS и запрашивает логин/пароль — деплой упадёт в этом месте. Надёжный вариант: клонировать по SSH и добавить на сервер deploy-ключ с доступом на read репозитория.

5. **После правок в workflow**  
   Изменения в `ci.yml` применятся только при следующем push в `main`. Запушь коммит с обновлённым workflow и снова посмотри запуск в Actions.
