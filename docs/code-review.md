## 1. Что сделано хорошо

- **Единая обработка ошибок**: `AppError` и `errorHandler` в `backend/src/errors.ts` дают предсказуемый формат `{ message }` и не светят внутренние детали в 500.

- **Запросы к БД**: везде параметризованные запросы (`?`), риска SQL-инъекций нет.
- **Типизация**: TypeScript на бэке и фронте, интерфейсы для API (User, Booking, UserPreferences и т.д.).
- **Роли и доступ**: проверки `req.userId` / `req.userRole`, владелец компании и владелец записи проверяются перед изменением.
- **Фронт**: централизованный API-клиент, интерцепторы для токена и 401, локализация сообщений об ошибках (API_ERROR_RU).
- **CI**: отдельные шаги backend (test + build), frontend (lint + test + build), E2E на Playwright, деплой с откатом при ошибке.

## 3. Рекомендации по улучшению

### 3.1 Валидация и санитизация

- **Регистрация/логин**: нет проверки формата email (регулярка или нормализация), длины имени/пароля (верхняя граница).
- **Текстовые поля**: `name`, `title`, `description` и т.п. сохраняются без ограничения длины; при желании — ограничить на бэке и/или в БД (например, `CHECK(length(name) <= 500)`).

### 3.2 CORS ✅ (B87)

Для продакшена настроен явный список разрешённых origin; в dev по-прежнему может использоваться `origin: true`.

### 3.3 Rate limiting

Нет ограничения частоты запросов. Для `/auth/login` и `/auth/register` имеет смысл ввести лимит (например, express-rate-limit), чтобы снизить риск перебора паролей и спам-регистраций.

### 3.4 Бэкенд: типизация `any`

В `bookings.ts`, `slots.ts`, `userEvents.ts` встречаются приведения к `any` (например, `row as any`). Имеет смысл завести типы для строк БД (например, `BookingRow`, `SlotRow`) и убрать `any`.

### 3.5 Фронт: хранение пользователя

`AuthContext` хранит объект пользователя в `localStorage` и восстанавливает через `JSON.parse`. Данные не подписаны — при компрометации localStorage можно подделать роль. Для текущего уровня приложения допустимо; при ужесточении требований — хранить только токен и при старте запрашивать `/auth/me` (если такой endpoint появится).

### 3.6 Тесты ✅ частично (B98)

- Бэкенд: добавлены интеграционные тесты для auth, companies, slots, directions, bookings, userEvents (в дополнение к user.ts).
- Фронт: часть страниц покрыта (Home, Login, Register, Companies, Bookings, MyCalendar и др.); при добавлении новых фич стоит дополнять тесты.

### 3.7 Схема БД: employee_directions

Таблица `employee_directions` ссылается на `employee_id` без FK на `users`. Если это задел под будущую сущность — можно оставить; иначе стоит либо добавить FK, либо кратко описать в комментарии/документации назначение таблицы.
